# 00 章程：这一轮到底做什么

- 立项：2026-11-12
- 决策人：用户（家长）
- 执行：主会话（项目经理）+ 多角色评审
- 前置资产：`design/ux-redesign`（设计包 + 原型）、`design/ux-round2`、`design/ux-round3`

## 1. 用户要什么（原话）

> 我已经通过 cursor 优化改进了一版项目，基本还是可以的……当前界面的实现看着还是可以的，已经优化过几轮了，暂时可以把当前的实现作为一个基准，然后在这个基础上优化改进，先尽量不改动原来的基础上重新基于之前项目的需求，提交，规划文件，通过多团队分析优化的方式，重启一个新的优化方案和工程。

拆成五件事：

1. 完整看清当前代码与三轮设计资产，不凭印象；
2. 把**现在这一版界面**当基准，不从零设计；
3. 基准原件不动，新工作另起工程（本目录）；
4. 先出规划文件，再动代码；
5. 多角色分析、评审、验收，不是一个人从头写到尾。

## 2. 这个工程不是什么

- 不是重做设计：视觉系统、信息架构、三条旅程已经过 M1–M8 门禁，不推翻。
- 不是接进产品：`runtime/web/` 本轮不改；界面先在本工程 `app/` 里做完、验完。
- 不是手机适配项目：主对象是平板横屏 1180×820，手机小屏不是优化对象（沿用 01_REQUIREMENT_BASELINE）。
- 不是一次性重写：`app/` 从基准复制，按轮次小步改，每轮可回退。

## 4. 成功的定义

做完这一轮，应该能说清三句话，且每句都有证据：

1. **能天天用**：孩子打开就知道今天做什么，做完一道题知道对错、为什么错、下一步点哪；中途离开再回来，进度还在。
2. **不再说假话**：界面上每个数字、每句状态描述都能在数据里对上；写死的「12.1 三角形」「回到今天」这类文案清零。
3. **能验收**：每个 P0/P1 问题都有对应判据，判据能自己跑出红/绿，不靠人眼看截图说「好像好了」。

## 5. 硬约束

- 视觉与版式：沿用基准的视觉系统（字号阶梯、色彩 token、圆角/间距档位），不新造第三套。
- 数据契约：页面只通过 `MC.data` 读 `runtime/web/data/*`，不直连 content、不写死题面。
- 记录契约：练习作答最终要落到产品同一套 key（`mc.records.v1`）的语义上，原型期用 `mc-proto-drafts` 隔离，迁移时必须给出映射。
- 每次改动都要能回答：改了哪个文件、为什么改、怎么验、失败怎么退。
