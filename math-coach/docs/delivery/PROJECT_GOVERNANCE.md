## 1. 规则优先级

本文件补充项目协作方式，但不能覆盖用户明确指令、宿主平台政策、安全边界、审批策略和仓库已有的更高优先级规则。发生冲突时，遵循更高优先级规则，并记录冲突和处理结果。

建议优先级：平台与安全规则 → 用户明确要求 → 仓库现有治理与项目约束 → 本项目治理文件 → Agent 自主建议。

## 2. 唯一事实来源

- 项目工作区是需求、决策、任务、问题和验收证据的权威来源。
- 聊天消息不能代替项目文档更新。
- 正式开展任务前，阅读本文件、`PROJECT_BRIEF.md`、`AGENT_REGISTRY.md`、`CURRENT_STATE.md` 及与当前任务相关的专业规格。
- 不同文档或文档与实际代码冲突时，不得静默选择一个版本；记录到 `DECISIONS.md`，由责任人处理。
- 事实、假设、推测、建议和未知事项必须分开记录。

## 3. Agent 能力真实性

- 角色说明文件不是已运行的 Agent。
- 配置文件存在不是模型调用成功。
- 模型能回复，不等于它拥有文件、浏览器、设计工具、终端或测试权限。
- `VERIFIED` 必须有一次真实、具有代表性的任务调用及证据。
- 额度只有在宿主明确提供状态时才能报告；否则填写 `UNKNOWN`。调用失败不能随意归因为额度不足，应记录实际错误。
- 可复用配置默认继承当前主 Agent 模型，不固定历史型号；若平台默认子模型设置会覆盖父模型，必须检查并说明。
- 不得伪造 Agent 身份、调用记录、并行状态、模型信息、工具权限、截图或测试结果。
- 平台没有独立 Subagent 时，可以由主 Agent 按角色顺序做审查，但必须标记为“角色模拟”。

## 4. 岗位权限边界

- 项目经理：负责范围、优先级、依赖、委派、进度、升级和项目记录；不能代替专业角色做全部判断。
- 产品分析师：负责用户和业务需求、需求分解、范围追踪和验收意图。
- UX 设计师：负责端到端体验、信息架构、任务流程、可用性标准和 UX 验收。
- UI 设计师：负责视觉系统、布局、组件、状态一致性和 UI 验收。
- 交互设计师：负责控件行为、状态变化、反馈、导航和错误恢复规格。
- 系统架构师：负责技术可行性、模块边界、接口、数据流、非功能要求和技术风险。
- 开发工程师：负责实现、代码质量、自测和实现说明；不能独自批准自己的工作。
- QA 工程师：负责独立测试、证据、缺陷记录、回归和质量建议。

小型任务可以合并岗位，但必须说明合并原因。涉及重大用户体验的任务，设计验收应与开发实现保持独立。

### 4.1 责任矩阵（RACI）

每项任务至少有一个 `A`（最终负责或批准）和一个 `R`（实际执行）。`C` 为必须咨询，`I` 为需要知会。不能出现无人负责，或几个角色都以为对方负责的情况。

| 工作事项 | 项目经理 | 产品 | UX | UI | 交互 | 架构 | 开发 | QA |
|---|---|---|---|---|---|---|---|---|
| 项目范围与计划 | A/R | C | C | I | I | C | I | I |
| 需求分析 | A | R | C | I | C | C | I | C |
| 整体体验评估 | C | C | A/R | C | R | C | I | C |
| 视觉规范 | I | C | C | A/R | C | C | C | C |
| 交互规格 | I | C | A | C | R | C | C | C |
| 技术架构 | I | C | C | C | C | A/R | C | C |
| 功能实现 | I | C | C | C | C | A/C | R | I |
| 测试与缺陷验证 | I | C | C | C | C | C | C | A/R |
| UX/UI 验收 | I | C | A/R | R | C | I | I | C |
| 发布准备 | A | C | C | C | C | R | R | R |

项目可以调整矩阵，但调整原因要记入 `DECISIONS.md`。项目范围和重要取舍的最终决定权在用户或其明确授权的产品负责人。

可选角色启用时才加入矩阵：安全审查对技术架构和发布准备为 `C`，无障碍对 UX/UI 验收为 `C`，发布运维对发布准备为 `R`。未启用则不要空出一列。

## 5. 任务契约与状态

每个实质性任务必须有稳定编号、来源、目标、负责人、输入、依赖、输出、验收条件、风险和状态。

任务、缺陷、文档、Agent 能力、结论和项目状态统一使用 `references/governance/status-model.md` 中的状态词，不另起一套。

实现、自测、测试和验收是不同事实。`IMPLEMENTED` 只表示交付物已产出并附自测记录，不等于 `DONE`。

## 6. 正式交接

交接内容至少包括任务编号、背景、来源、现有决策、约束、输入文件、预期输出、验收条件、依赖和已知风险。接收方需要确认收到，或明确指出缺少什么。仅发送一个提示词不代表交接完成。

## 7. 设计与开发顺序

实质性用户界面改动应先形成当前状态证据、用户任务、UX 发现、交互行为、UI 规格和技术可行性评估，再进入开发。经批准的紧急修复可以使用缩减流程，但必须记录省略的步骤及原因。

架构评审至少覆盖已有能力复用、受影响模块/接口、兼容性、性能、安全与隐私、数据迁移、可观测性和回滚。

## 8. 并行工作和文件所有权

- 只有输入、输出和依赖清晰且相互独立的任务才能并行。
- 每份共享文档或同一代码区域同时只能有一个明确写入负责人。
- 多个 Agent 修改相关代码时，先划分边界并指定集成负责人。
- 禁止无协调地并行覆盖同一个文件。
- 合并后由集成负责人解决冲突、运行测试并记录被采纳的结果。

## 9. 仓库保护和安全

- 修改前检查分支、未提交改动和工作区状态。
- 保留用户已有改动，不执行无关清理。
- 未经授权不得执行 `reset --hard`、强制推送、删除目录、生产数据迁移、线上发布、权限更改或付费动作。
- 不把令牌、密码、私钥、个人敏感资料写入项目文件或日志。
- 大范围修改前建立版本控制提交点或可恢复备份，并给出回滚方式。

## 10. 需求变更管理

已批准范围发生变化时，必须分析需求、UX/UI、架构、依赖、工作量等级、测试、数据和发布风险的影响。由项目经理登记变更；涉及目标、范围或用户价值的变化，应由用户或其明确授权的产品负责人批准。

## 11. 质量门禁

- 实质性功能进入开发前，需求必须可理解、可测试，设计与架构约束已就绪。
- 没有适当测试证据，不得验收任务。
- 关键或高优先级缺陷、安全/数据风险未解决或未经明确接受时，不得建议发布。
- UX/UI 规格与实际运行效果不一致时，必须记录并退回修改，或由有权负责人接受偏差。

## 12. 完成条件

项目或迭代完成时，必须核对范围、记录验收、关闭或明确接受高风险问题、记录测试和已知限制、完成代码及文档交接，并明确下一负责人和当前状态。

## 13. 会话交接

子 Agent 只在当次会话内存在，下一次会话不会记得上一次聊过什么。项目能接着做下去，只靠项目文件。

- 每轮工作结束前，更新 `PROJECT_STATE.json` 的 `last_updated`、`next_actions`、`blockers` 和任务计数，并在 `ITERATION_LOG.md` 追加一行。
- `next_actions` 每一项写清楚：做什么、关联编号、建议角色、需要先读哪些文件。
- 新会话开始时按 `references/workflows/session-continuity.md` 恢复，不凭记忆续做。
