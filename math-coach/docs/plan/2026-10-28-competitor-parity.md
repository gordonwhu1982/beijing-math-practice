# 竞品对齐：界面元素 → 需要的底层能力 → 架构调整

> 依据：docs/analysis-2026-10-teacher-kg.md（三片录屏的逆向分析，权威）、docs/plan/2026-10-28-ux-overview-redesign.md（体量实测与三档方案）、仓内数据与前端代码实测（2026-10-28）。
> 决策（用户 m08310）：**按参考产品来，最终界面尽量照竞品设计**。本文回答「为此需要哪些底层能力、架构改哪里」，并给出可执行的排序。

## 0. 三句话结论

1. 竞品的界面之所以「像一个整体」，不是画得好看，而是它有**三样我们现在没有的底层产物**：多分辨率的视图数据（一屏给出聚合后的结构）、带方向语义的两种边、以及每个节点的**计数**（方法连几个点、这个点有几条关联）。
2. 我们缺的**大部分不是内容，是派生层**：边表 5265 条已 100% 带 evidence，16 个思想全部跨 2–6 册，673 点全部挂上方法，148 点有课标（这四个数是阶段 A 之前的快照；现状边 6334、课标边 981 覆盖 666 点、题→点 2576，见 §5 各节与 docs/STATE.md §3） —— 这些数据前端一条都没用上（is_part_of 842 条在运行时 0 处引用）。
3. 真内容缺口只有 4 项且都能切小：方法前后置（原 16 条，现入表 395 条、覆盖 337/667 个方法，其中 379 条是逐条起草）、课标覆盖（148/673）、题→点映射（243/2708）、素养认定（现为派生）。前两项决定竞品那种「方法页有前置/后置」「每点有课标原句」能不能立起来。

## 4. 架构调整（4 处）

### 4.1 build 层：从「一份图」变「三份视图 + 一份索引」

现在 tools/build_web.py 只产 data/graph.js（1664 节点 / 5265 边 / 689KB）与 147 个节切片。新增两个产物：

- data/view.js：三档视图的结构（哪些节点、哪些边、聚合边怎么折叠、每个节点的尺寸档）。**坐标不进产物**，仍由前端手算（现有 packIsland 就是为了布局稳定可控）。
- data/index.js：计数索引。

理由：聚合与分级是数据问题（要知道章边界、边类型、计数），在 build 层算一次，前端只做「按当前档位取子集」；切档不用重新请求，体量也远小于把 673 点全量塞首屏。

### 4.2 schema 3.2：加 4 个字段，不加实体

- node：counts（由 P2 生成，运行时只读）、tree_path（如 801/12/12.1）
- edge：tier（1/2/3，派生）、dir（如 skill->kp，承载「两种边」的方向语义）
- thought：coverage（覆盖册数与点数，派生）
- kp detail：competency_status（derived／reviewed）

契约其余部分不动：Git JSONL 仍是唯一权威，build 产物全部可重建、进 .gitignore。

### 4.3 前端：三档替代六视角，容器框替代「岛」

现状 runtime/web/js/views/map.js 的六个视角是「按实体类型切」，竞品是「按分辨率切」。改成：

- state.scope = overview | chapter | focus；state.layers = {skill, thought, cp, mc} 四个开关
- 布局：容器框由 P4 的 tree 决定；章内列由先修决定（把 layersOf 从「只认同节」放宽到「同章」）
- LOD：zoom < 0.18 圆点无字 / 0.18–0.45 小方块 / 0.45–0.85 卡片截断 8 字 / >0.85 现状
- 悬停：只亮一跳邻居 + 显示「N 条关联 · 依据」（读 edge.evidence）

六视角里 skeleton / misconception 降为叠加层，thought 变「思想总表页 + 从节点长出去的一页」，chart 成为 scope=chapter。

### 4.4 明确不动的东西

数据契约（JSONL 权威、SQLite 只做构建缓存）、判题三态、作答记录 outbox、check_all.sh 闸门结构。竞品有而我们不做的已在 UX 方案 §7 列过（力导向、拖拽、教材原页、素养第七视角）。

### 5.2 阶段 B 第一步落地实测（2026-10-28）—— 分辨率自适应

先做这一层，因为 P4 容器框要按分辨率加：尺寸不稳，容器加了也量不出效果。

| 项 | 计划 | 实测 |
|---|---|---|
| P1 三档产物 | build/view.js 三份视图 + index.js | 没另起产物：档位是「看得多远」的运行时状态（scopeOf 从 view 与 vol/ch 推出来），不进数据。理由同阶段 A——档位与坐标一旦进 JSON，等于把布局算法冻在数据里 |
| SC 分辨率 | 计划里没有 | 新增 SCOPE_K：overview / chapter 1、book 0.62、repo 0.34，同时缩卡片尺寸、间距、截断字数，三者必须一起缩 |
| 六册档取消岛 | 原属 P4「容器框替代岛」 | 先做了取消：673 个点分 143 个节岛，每岛还要标题与内边距，等于把画布拿去装边框。六册档改成一个网格，整册档保留 27 个节岛 |
| 岛内列数 | 写死 1 / 2 / 3 | 按画布宽算，再按「别排成一条竖线」收一档 |
| 岛网格列数 | 写死 4 列 | 按平均岛宽算，上限 8 列 |
| 章图整册档 | 一列 | 按宽度并 2-3 列（高 2299 → 1181） |
| fitView | 按全部元素取景 | 只按节点：边是连出来的，曲线会飞到内容外，算进 bbox 会把图缩得更小 |

撞出来的四个真 bug，都是「布局尺寸」与「渲染尺寸」两套尺寸打架：

1. 标签比卡片宽。shortOf 默认截 10 个字，六册档卡片只有 48 宽，10 个汉字 115px 横穿三个格子。改：截断长度跟 clipN() 走（3 / 6 / 8 字），并把 clip 补的省略号算进去（预留 clipN + 1 个字宽）。
2. lod0 / lod1 写死尺寸（28x28、44x24）。布局按 48x11 排、渲染画 44x24，高是行距的 1.5 倍，skill 视图因此有 1321 处重叠。改：四档全部走 data(w) / data(h)，LOD 只决定画不画字、画成什么形状，不决定大小。
3. underlay 与边框计入 bbox。有题节点的 underlay padding 与边框都算进 renderedBoundingBox，而间距被 SC 缩到 5，行与行就压在一起。改：间距基准 14 → 18 且下界 8，underlay padding 也按 SC 缩。
4. 六册档 143 个岛写死 4 列，排成 36 行，画布高上万像素。

### 5.9 内容线 D4 落地实测（2026-10-28）—— 素养从一条两跳链变两层

计划：给素养加 competency_status（derived／reviewed），先全 derived，逐章转 reviewed。

原因是两跳链（知识点 → 方法 → 思想 → 素养）有两个问题：

### 5.10 阶段 B 第二步：跨节依赖怎么上章图（2026-10-28）

§5.2 里留了一句「章内跨节先修纳入布局待做」。这一节是那条尾巴的落地。

**问题**：章图（chart 视图）里每一节是一个岛，岛内按先修分层，但**同章跨节的先修一条都没画**。数据里有 152 条同章跨节的 prerequisite_of，图上一条看不见——孩子读一章时看到的是 12 个互不相干的岛。

**三个候选方案与取舍**：

| 方案 | 做法 | 否决 / 采纳的理由 |
|---|---|---|
| 逐条点级边 | 每一条跨节 prerequisite_of 都从源点画到目标点 | 边要横穿好几个岛，第 12 章会多出几十条长线，整张图糊掉 |
| 纳入布局 | 把整章的点当一张图重新分层，节不再分岛 | 等于放弃「章图」这个视图本身；节是孩子找东西的锚 |
| **节间聚合线（采纳）** | 一对节之间画一条线，线粗 = 这一对之间有几处依赖 | 一节一对最多几十条，不糊图；保留「哪几节彼此咬着、咬得多紧」；具体是哪两个点，进节里看 |

**实现**（`runtime/web/js/views/map.js`）：

- `secDepPairs()`：扫全库 prerequisite_of，只留两端都是知识点、同册同章、不同节，按「节对」计数，缓存在 `depPairCache`（`index()` 里清空）。
- `addSecLinks(packs)`（原 `addSecSeq` 扩写）：节对 A→B 有线时，取 A 最右的点作源、B 最左的点作靶，画一条 `x="dep"` 的边，宽度 `max(0.9, min(2.6, 0.7 + 0.22*n))` 写进 `data.w`；教材顺序那条细虚线原样保留。
- 样式：`edge[x="dep"]` 用 `width: data(w)`、翠绿但 opacity 0.5 —— 它是一条汇总，比人工确认的单条先修淡。
- 图例加一行「节到节的粗箭头 = 后一节有几处要用它」；LEAD 文案（视图说明）同步。

**撞出来的 bug（断言抓到的）**：第一版 `dep=0`，一条都没配上——因为计数用的是 `a.sec`（`12.1`），而岛 key 是 `secIdOf` 的形态（`S801-12.1`），两边拼出来的 key 永远不等。改用 `secIdOf(a) + "|" + secIdOf(b)` 后对上。这类「两个模块各自拼 key」的错误只会在运行时静默返回空集合，必须靠断言把数量钉住。

**实测**（第 12 章，画布 1180x559）：跨节聚合线 **19 条**，最大一对之间 **7 处**依赖，线宽分布 0.92 / 1.14 / 1.58 / 1.8 / 2.24 五档；教材顺序虚线仍 11 条；卡片与标签重叠均 0。断言 `map-chart` 现在钉三件事：dep ≥ 1、depMax ≥ 1、图例含「后一节有几处要用它」。

**诚实边界**：聚合线只回答「这两节之间有依赖、有几处」，不回答「是哪两个点」——后者要进节（或点开节点看三列）才知道。它是导航线索，不是依赖清单。

**方法 → 方法这 395 条是怎么来的**（2026-10-28 第二批）

规则反推两次被抽检否决：第一版按「点级先修一跳反推」得 821 条，抽 40 条只有 50.0% 站得住；收紧到只用人工点级边得 264 条，抽检反而更差（27.5%）。病根是点级先修回答「能不能学这个点」，方法级问「先练哪条做法」，一个点上常挂好几条不同做法，点与点的先后推不出做法与做法的先后。于是整段规则删除，改成**逐条起草**：

顺带记一条判据：跨章同册与跨册边里有一批是「册与册之间串门」（例如八上第 10 章分式用到七下整式的运算）。这类边不是错，而是**告诉孩子「这一节要回头翻七年级的书」**，正是竞品把教材位置标到每个点上的那个理由。

### 5.12 按类型搜：E5 标签的轻量做法（2026-10-28）

竞品左栏有标签筛选。我们没有 tag 实体，但手上有三类真分类：知识点的 `kp_type`（11 类：概念 / 定理 / 性质 / 技能 / 方法 / 公式 / 表示法 / 事实 / 模型 / 情境 / 活动）、方法的 `tier`（核心 / 拓展 / 竞赛）、以及已经做成筛选行的核心素养。原来的判定是「暂不做」，试搜之后发现一个真缺口：检索串里写的是**英文枚举**（theorem、olympiad），孩子搜「定理」「竞赛」命中 0 —— 这是「想不到就搜不到」的同一个病。

做法（`tools/build_web.py` 的 `_sch()`）：加两张中文映射 `_KPT_CN` / `_TIER_CN`，检索串里换掉英文枚举，不新开筛选行。理由是筛选行与搜索回答的不是同一个问题——筛选行把**当前这一屏**缩小，而「找出全库所有定理」是跨册检索，本来就该走搜索。

实测（全库检索串命中数，子串统计）：

| 搜的词 | 知识点 | 方法 |
|---|---|---|
| 定理 | 101 | 25 |
| 性质 | 138 | 63 |
| 概念 | 171 | 6 |
| 公式 | 49 | 21 |
| 技能 | 105 | 0 |
| 竞赛 | 0 | 24 |
| 拓展 | 0 | 66 |
| 核心 | 0 | 577 |
| theorem / olympiad（英文） | 0 | 0 |

面板仍是「最多 40 条候选、列前 8 条、底部写共 N 个，先列前 8 个」。断言 `search-type` 钉四件事：搜「定理」共 ≥ 20 个、搜「竞赛」首条是 `SK-`（竞赛级方法是方法不是知识点）、搜英文 `olympiad` 命中 0、两次搜索都不跳图且无 console error。冒烟 39/39。

### 5.14 该抽回来看看：规则式复习（2026-10-28）

做对过的题不等于记住了。#/weak 能回答「哪里不稳」，但那一页只数「错着没改」，对「当时对了、现在未必」的题一声不响。今日页补一块，只做一件事：到期的旧题抽回来。

**规则**（写在代码注释里，也写在页面上）：同一道题按做对过的次数推间隔 —— 第 1 次对后 3 天、第 2 次对后 7 天、第 3 次起 21 天；到期就抽，最多 5 道，超期倍数高的先抽。做对一次往后推一档，做错自然回到「待改」。

**为什么不直接上 SRS/FSRS**：现在的作答量撑不起算法式的间隔重复（八上 57 个知识点要 14 次/点才勉强可启参数），跑出来的参数是噪声。这条规则可以被家长一句话复核（「对过三次的隔三周」），算法不行。等记录上千条再回来谈。

**实现**：`runtime/web/js/views/today.js` 新增 `GAP_DAYS = [3, 7, 21]` 与 `dueReview(limit)` —— 按 item 归并，只认最后一次是 correct 的题，`gap = GAP_DAYS[min(ok,3)-1] * 86400000`，按 `ratio = (now - last.ts)/gap` 排序取前 5。区块插在「还欠着的题」之后、近七天之前；每行写「N 天前做对过 · 档位」并给「就这道」，底部一个「抽 N 道看看还在不在」直接调 `MC.practice.startMixed`（复用错题重练的混合队列，跨节也能一次做完）。点击用 `host.onclick` 不用 addEventListener —— 这仓已经因监听叠加坏过两次。

**断言** `review-due`：造一条 5 天前做对的记录（题 id 前缀取真实节号，否则 startMixed 找不到题）→ 今日页出现「该抽回来看看」「5 天前做对过」「抽 1 道」→ 点它断言「第 1 / 1 题」且有作答控件 → 清理记录、无 console error。冒烟从 40 到 **41/41**。

**边界**：① 只按题算，不按知识点算（同一个点的三道题互不相干，「这个点该不该复习」仍要人看）；② 没有时间衰减权重，只有三档固定间隔；③ 记录早于这个功能的老题不会被补抽；④ 抽回来做对只把间隔往后推，不区分「当时是带提示做对的」（记录里有 hint 字段，页面上标了，间隔没区别对待）。

### 5.15 依据总览：把「哪来的」摊成一页（2026-10-28）

竞品的最后一条微文案是「每条关联，都有依据」。我们的依据确实存在（边的 evidence、方法的 boundaries、题到知识点的 basis），但散在三处：图的悬停、详情面板、docs 里的长文。家长不会翻三处。

新页 `#/evidence` 只回答两件事：这个数字是怎么来的、它算不算硬。三块内容 ——

1. **关系边按依据分三档**：人工判定 / 规则推断 / 方法挂点推断，各多少条、占多少，并写清每档「能信到什么程度」（人工的是逐条看过写了理由；规则的是脚本推的可复跑但没逐条看；方法挂点推断是从「方法挂在哪几个点」反推的，最容易错）。图上的线粗细就是这一档。
2. **四类实体各自的底气**：知识点（定义 100% 有、挂课标多少、挂方法多少、能往前追多少）、方法（核心多少、还是草稿多少、知道先练哪个的多少）、题目（有题的节多少、判不了会怎么说、错题怎么进待改）。
3. **一行复核命令**：check_all.sh / skill_prereq_check.py / questions_kp_check.py / relations_check.py —— 想自己验一遍就照抄。

**关键取舍：页面里没有一个手写的统计数字**。全部从 `graph` 与 `catalog` 现算（边按 `x` 分档、覆盖率按 `cpstd` / `cnt.sk` 数、题数按 catalog 累加）。这一页的全部意义就是「不悄悄过期」，抄进来的数字第二天就开始过期。

**断言** `evidence-facts`：读页面里的三档数字本身（不是读标题）——人工 1386、规则 4553、挂点 395，三者之和 > 5000 且规则多于人工，13 行、4 条命令、文案含「草稿」。加一条路由断言钉首屏不空。冒烟 41 → **43/43**。

**边界**：这一页只说「多硬」，不说「对不对」——一个规则推断的边也可能判对了，只是没人逐条看过。真正的复核记录还在 edges.jsonl 的 evidence 字段与 docs 里，页面只是指路。

### 5.16 沿着教材走：节页与练习结束都能接下一节（2026-10-28）

孩子按教材顺序学，界面却一直要人「回目录、找下一节、再点进去」。三跳里有两跳是界面造成的。补上 `neighborsOf(vol, no)`：同册按教材顺序摊平，取前一节与后一节，跨章也接续。

- **节页**底部多一块「接着走」：‹ 上一节 / 下一节 ›，下一节没题时按钮降为空态样式并写「（还没有题）」，有题时补一句「下一节有 N 道题，进去就能练」。
- **练习结束页**的「接下来」多一张「下一节 · 12.2」卡：下一节有题就直接进练习，没题就进节页看知识点。跨节混合队列（错题重练）不显示这张卡——那条路本来就不在教材顺序上。

**为什么不顺手把「上一节 / 下一节」放到顶部**：顶部是标题与进度，孩子这一屏的动作是「练」，不是「跳」；底部才是「这一节完了，去哪」。

**断言** `section-next`：进 12.1 节页，断言「接着走」区块存在、恰好两条链接、带 › 的那条 href 是 `#/sec/801/12.2` 且不是当前节。冒烟 43 → **44/44**。

### 5.17 目录页回答「学到哪了」（2026-10-28）

「哪里不稳」按知识点讲问题，但家长打开目录时想知道的是另一件事：**按教材顺序，我们走到哪了**。这两件事数据同源，口径必须一致——都只看每道题最后一次作答。

- **节行**在「知识点 N · 题 N · 方法 N」后面补「做过 n/m · 独立对 k（带提示 h）」；带过提示做对的不计入独立对，否则进度会虚高。
- **册头**一条细进度条加一句「做过 n / 共 m 题（p%）· 独立做对 k」。进度条宽度固定 72px，百分比只做视觉提示，数字写在旁边——不让人靠眼睛量长度。
- **章头**补「N 题 · 做过 m」。
- 实现上给 `MC.store.bySec()` 的返回值加了两个字段（`last` 每题最后一次结果、`h` 是否用过提示），没改原来的 items 结构，目录页与节页的旧用法不受影响。

**顺手改掉的一处偷懒**：原来 `secRow` 里 `href` 有 `var href = s.q > 0 ? ... : ...` 两个分支写的是同一串，直接合并。

**断言** `toc-progress`：清空记录 → 写两条（一条做对无提示、一条做错）→ 进 `#/toc/801`，断言节行含「做过 2/84」「独立对 1」、册进度含「做过 2 / 2708 题」「独立做对 1」且进度条宽度非空。第一次跑是 FAIL，原因不是代码错，而是**ran 断言前没有先清空记录**：前面几条断言真的做了题，12.1 的「做过 2」是残留记录凑出来的巧合，册级累计却不是 2。教训写在断言里：造基线数据要先清场。冒烟 44 → **45/45**。
