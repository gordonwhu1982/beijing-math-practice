## 1. 字段级缺口（8 条）

### G1 registry 缺三个被文档承诺的键：`public_fields` / `visibility_rule` / `mastery_spec`

- **缺什么**：`schema.json` 顶层只有 `enums / id_rules / entities / capabilities.list(9 项) / interfaces / enum_aliases`。§6 第 1 条说「public 切片只按 registry 里登记的 `public_fields` 逐字段拷」（243 行），§14#3 说「字段白名单由 registry 的 `visibility_rule` 生成」（359 行），§14#2 说「输入 registry 里的 `mastery_spec`」（358 行）——三个键都不存在；同一格还写着「新 `mastery_spec.json`」，同一文档两处口径互斥。
- **会导致什么实际问题**：`check_no_leak.py`/`check_license.py`（§9 闸门 2/3）没有白名单输入，只能把字段名硬编码进脚本——这与「脚本里不写死字段名」（`schema_check.py` 第 14 行）的自述直接冲突；掌握度参数留在代码常量里，改阈值要改代码、无法 diff。P1 之后 1128 题都有 `answer_spec`，没有白名单就没人能自动回答「`answer_spec.canonical` 会不会漏进 public 切片」。
- **最小改法**：registry 顶层加三个键，键值直接可读：

```json
"public_fields": { "question": ["uid","version","stem","form","band","figure","kp_tags","license","visibility"],
                   "knowledge_point": ["uid","canonical_name","kp_type","definition","conditions","objectives"] },
"visibility_rule": { "stem_public": { "exclude": ["answer","answer_spec","answer_note","solution_steps","rubric_ref"] },
                     "full_private": { "exclude": [] },
                     "internal_only": { "exclude": [] } },
"mastery_spec": { "window_days": 42, "min_evidence": 3,
                  "levels": { "independent": {"min_independent": 3,"min_acc":0.8},
                              "hinted": {"require_hint_level": "L3_method"},
                              "inferred": {"allow_inferred": false},
                              "unstable": {"recent_wrong_ratio": 0.34},
                              "weak": {"min_acc": 0.5} } }
```

并在 `schema_check.py` 加 10 行自检：文档 §6/§14 引用的 registry 键必须存在，缺失即 error（否则这类「文档承诺、契约缺位」会继续复发——`test_paper`/`study_goal` 就是同一病，见 §4 第 6 条）。

### G2 嵌套结构没有类型定义，校验器只查顶层是否非空

- **缺什么**：`entities.*.fields` 全部是自然语言句子（如 `"answer_spec": "{canonical, equivalent[], tolerance, unit, unordered, answer_type}；unordered=true 覆盖 152 道…"`），没有任何 `type`/`required_keys`/`item_keys`/`enum_ref`。八个嵌套结构（`answer_spec / difficulty / validation / kp_tags / solution_steps / evidence / review / source`）没有一个有机器可读形状。
- **会导致什么实际问题**：`validate()` 第 163–169 行只判 `r.get(f) not in (None,"",[],{})`，所以 `answer_spec: {"x":1}` 与完整 answer_spec 在 gaps.csv 里都是 **100.0 ok**。P1 的「answer_spec 100% / difficulty 四轴 100%」可以被任意垃圾 dict 满足；`enums.answer_type`、`enums.difficulty_axis_course`、`enums.judge_how`、`kp_tags.role` 这四个已定义枚举**从未被校验**（`chk_enum` 只覆盖 7 个顶层字段，第 190–196 行）。
- **最小改法**：每实体加一个 `schema` 子块（只覆盖这 8 个结构即可，不进 public 切片）：

```json
"question": { "schema": {
  "answer_spec": { "type": "object", "required_keys": ["answer_status","values","order_policy","answer_type","how"],
                   "keys": { "answer_status": {"enum": ["present","missing","needs_review"]},
                             "order_policy": {"enum": ["any","strict","set"]},
                             "answer_type": {"enum_ref": "answer_type"},
                             "how": {"enum_ref": "judge_how"},
                             "values": {"type": "array", "item_keys": ["raw","kind","role"],
                                        "item_enums": {"kind": ["number","expr","set","tuple","text"],
                                                       "role": ["canonical","equivalent"]}} } } } }
```

配一个 `tools/schema_shape.py`（100 行内，纯 stdlib，不引 jsonschema），输出 `build/report/schema/shape.txt`。**注意不要塞进 `schema_check.py` 的 error 计数**：否则 P1 第一步就会把 16797 变成 22437，验收曲线失去单调性。

### G3 `answer_spec` 缺 answer_status/values[]，且 `unordered` 默认方向与判题规格相反

- **缺什么**：① `answer_spec` 的第一项是 `canonical`，一个字符串——但实测 1092 题答案首行是自然语言句子（12.1_bas_01：「满足条件的三角形共有 `$2$` 个，每组边长为 `$(2,4,4)$`、`$(3,3,4)$`。」；1092 题还统一带 `数字.【解】` 前缀）。② 36 题 `answer_status=missing`（全 basic，id 后缀 `_err_`，即「找错」题，答案在解析里而不在结论里），`answer_spec` 没有承接缺失态的位置。③ 设计规格 §3 的 L2 明写「**默认无序**，`ordered:true` 才按序」，registry 用的是 `unordered`（缺省 false），语义方向正好相反。
- **会导致什么实际问题**：P1 按现结构落盘，`canonical` 会装 1092 个句子，判题器只能全部退 `manual`——「98/120 判错」会升级成「1128/1128 判 manual」；36 题则永远无法表达「这题没有可判答案」。而 `unordered` 一旦按 false 批量写死，实测 154 道多值题（answer 首行去前缀后含「、」127 或「或」28，去重 154；文档 §5.2 写 152，口径基本一致）会继续被判错，且因为 evidence 只追加，误判 verdict 无法回收。
- **最小改法**：把 `answer_spec` 定成 `{answer_status, values:[{raw,kind,role}], order_policy: any|strict|set, tolerance, unit, answer_type, how}`，硬规则：`order_policy` 缺省 `any`（与 spec §3 对齐）、`how` 取 `enums.judge_how` 且 `how=manual` 时 `values` 可为空、`answer_status=missing` 时 `values=[]`。旧字段 `unordered` 不写进 registry（P1 一批 1128 条还没落盘，此时改零成本）。

### G4 `kp_tags` 没有来源与置信度

- **缺什么**：`kp_tags: [{kp_uid, role, weight}]` 三项，没有「这个标签怎么来的」。而 P1 的唯一来源是 `tools/questions_kp_map.py`（2-gram + idf，只在题所属节的知识点里选），产出的 `status` 是 `auto_top3 / auto_single / no_candidate`。
- **会导致什么实际问题**：`kp_tags` 是必填字段，一旦写入就在概念上等于「已确认的 assessed_by 边来源」；但实测 854 题是多候选、261 题 top1−top2 分差 <0.1、149 题完全无候选。掌握度按 `kp_tags` 聚合时，等于把 2-gram 猜测当实测——这就是「57 个点做 15 题报 57 个掌握」的翻版（现在放大的是标签，不是题）。更麻烦的是**撤销成本**：没有来源字段就无法「只回滚自动标签」，只能全量重算。
- **最小改法**：`kp_tags[]` 加两个键：

```json
"kp_tags": [{ "kp_uid": "K801-12.1-01", "role": "primary", "weight": 1.0,
              "source": "auto_top3", "confidence": 0.61 }]
```

规则写进 registry：`source ∈ {manual, section_inherit, auto_top3, auto_single}`；`role=primary` 只允许 `manual | section_inherit`；派题与掌握度只读 primary，secondary 仅供检索与提示。

### G5 `id_rules` 从未执行，且 question 正则与真实 ID 家族不符

- **缺什么**：`schema_check.py` 全文没有一处 `re.`，`id_rules.pattern_by_kind` 六条正则一条都没跑。而 `question` 那条只许可 `(bas|std|adv|cha|com)`，实测 1128 条 id 的后缀是 int 265 / bas 261 / adv 200 / cha 171 / com 165 / err 36 / sel 10 / fill 8 / calc 6 / solu 6（`zm_` 与 `bt_` 前缀家族共 96 条）——**388 条不匹配**。KP（673）与 section（143）的 id 全部匹配，问题只在题目家族。
- **会导致什么实际问题**：P1 第一步要给 1128 题发 uid（`801-<id>`）。按现正则，388 个 uid 天生非法；更糟的是现在没人报，等 G2 的类型校验接上会一次性爆 388 条，届时 uid 已经被 `rubric_point.qid` 之外的引用点、切片 manifest、以及未来的 `learner_evidence.item_uid` 引用，改 ID 等于改历史。
- **最小改法**：正则放宽为 `^([0-9]{3}-)?[0-9]{1,2}\.[0-9]{1,2}_[a-z]{2,4}_[0-9]{2,3}$`，把家族词表移出正则，单列 `id_rules.families.question = {bas:"basic", std:"standard", adv:"advanced", cha:"challenge", com:"competition", int:"intermediate", err:"error-finding", zm:"chapter-test", bt:"textbook"}`，并要求「新家族必须先登记再使用」；`schema_check.py` 加 `--id-rules` 校验（uid 与 id 各一条正则），承接 G2 的类型校验一起跑。

### G6 `question.source` 与 adapter 契约的键完全不同，且没有「含真题成分」标记

- **缺什么**：`interfaces.adapter` 规定外部源产 `provenance{url, sha256, license, fetched_at}`；`question.source` 实测是 `{of: "ch12_index.json", gen_md5, ans_md5, origin}`，registry 也没定义 `source` 的类型。而实测 `trace_possible=true` 有 **336** 题、5★ 有 **165** 题——这些题的「真题成分」只体现在一个 boolean 上，没有任何来源证据。
- **会导致什么实际问题**：§6 的许可闸门要按 `license.class` 生成 public 切片，但数据里没有 `source_kind`/`url`/`sha256`，无法自动判定「这题能不能只放题干、要不要标 `redistributable=false`」。将来仓要公开时，只能人工重审 1128 题 + 逐条溯源 336 题；而这正是当初定「4–5★ 只放题干」时想避免的人工成本。
- **最小改法**：`source` 定为 `{kind(source_kind), ref, url, sha256, fetched_at, origin_id}`，新增 `enums.source_kind=[own-ai-draft, textbook, exam-ocr, web-derived, derived]`；`questions_check.py` 加一条可执行规则：`kind ∈ {textbook, exam-ocr, web-derived}` 或 `trace_possible=true` → `visibility` 必须 `stem_public` 且 `redistributable=false`（现有 336 题已满足，等于把隐式规矩变成闸门）。

### G7 `edge` 没有自然键唯一性，也没有合并证据位

- **缺什么**：没有 `natural_key`、`merged_from[]`、`conflict_with[]`；`schema_check.load_edges()`（113–136 行）把派生 + `prerequisites.json` + `kp_prerequisites.json` 三源**直接相加，不去重**，于是 gaps.csv 报 1493 行。
- **会导致什么实际问题**：实测唯一 `(src,dst,kind)` 只有 **1182**：派生文件内部已有 54 组重复，而 `prerequisites.json`（159）与 `kp_prerequisites.json`（98）**全部已包含在派生文件里**（subset 校验为 True），被二次导入 → 重复 311 行。后果不只是数字虚高 26%：DAG 校验与「补缺路径」会把同一先修关系重复计入深度，节级深度不可信（实测 12.9 与 12.10 的深度就是判成 0 的）。
- **最小改法**：registry 给 edge 加 `natural_key: ["src","dst","relation"]` + `merged_from[]` + `conflict_with[]`；`load_edges()` 改为「按 natural_key 合并 + 打印 `rows/unique/dup`」，gaps.csv 的 edge rows 换成 unique 数；P2 验收锚点从「1493 → 单文件」改为「unique 1182 全带 uid/review + 重复 311 行全部登记 `merged_from`」。

### G8 校验器读的是投影，且 `status` 枚举读错词表 —— P3 的产物本来就测不到

- **缺什么**：`load_curriculum()`（65–77 行）与 `load_kp()`（86–96 行）都把源记录**重建成 10 个固定键的 dict**，而「未登记字段」检测（170–175 行）作用在这个投影上；第 193 行 `chk_enum("knowledge_point", recs["knowledge_point"], "status", "review_status")` 用 `review_status` 五值词表去校验 `status`，而 registry 里 `knowledge_point.status` 取的是 `enums.kp_status`（title_only / draft / reviewed / verified）。
- **会导致什么实际问题**：① 往 `knowledge_points/801.json` 加 `definition / conditions / kp_type` 后，`nodes.jsonl` 投影把它们丢掉，`schema_check` 一律看不见 → P3 的验收点「第 12 章 99 点六字段 100%」**在当前校验器下不可测**；② `status` 按 registry 写 `title_only` 会立刻被判 673 条非法，写 `ai_draft` 反而合法 → 「574 点显式 title_only」这条 P3 验收同样无法证明；③ report.txt 里「未登记字段 0 类」是测量假象（`volumes/*.json` 里的 `source`/`edition` 从未进入被检查的对象；volume 的 `edition_id=0% / provenance=0%` 也是因为文件里叫 `edition`/`source`）。
- **最小改法**：`load_*` 改为「读原始记录 + 只注入 uid（不改键集）」，让未登记字段检测真正生效；`chk_enum` 改读 G2 的 `schema.<field>.enum_ref`，删掉 190–196 行的硬编码；`status` 与 `review_status` 分字段后，**词表切换必须与 P3 的数据迁移同一个 commit**（否则 673 条立刻变红）——这本身就是「契约与数据不同源」的代价，见 §3。

## 3. 最容易导致日后返工的三处设计

### R1 `answer_spec` 把「答案值」「判题模式」「缺失态」压成一个扁平对象，且默认有序

代价：判题器与回归集被字段形状绑死。spec §3 的 L0–L4 分层里，每层要读的键不同（L1 要 `values[].kind=numeric`，L2 要 `order_policy`，L3 要 `how=sampled`），扁平结构下每个实现都要写「如果 unordered 缺省则…」这类特判；改形状要重跑 1128 题回归，而回归结果会写进只追加的 `learner_evidence`——历史 verdict 无法回收，只能靠 `item_version` 递增来区分，而 `version` 的递增条件现在还没定义（G2 之外）。错误成本不对称：判错会污染掌握度，而标签错可以重算。

### R2 `kp_tags` 同时承担三个语义，却没有「标签版本」

代价：它既是 `assessed_by` 边的来源（§5.2）、又是派题单位（§8 M3）、还是掌握度的聚合键（§5.5），但 `learner_evidence` 只记 `item_uid + item_version`，没有记「当时的 kp_tags 是哪一版」。一旦 P4 把 261 题的可疑 primary 改掉，两周积攒的证据就无法复现「当时聚合到哪个 KP」，掌握度视图的 `confidence` 会变成不可审计的数字。修法不是加表，而是让 `kp_tags` 的变更必须 bump `item_version`——这需要在 P1 就把规则写进 `version` 的递增条件里，晚一步就要改 1128 题的 version 历史。

### R3 题目归属只往 `kp_tags` 走，`topics` 是 legacy

代价：`question.required` 里没有 `topics`/`section_no`（二者都在 `legacy_fields`），v3 目标态下题目可以完全没有「哪一节」的锚点。但实测 107 题是章级（`topics_scheme=chapter`，`section_no=null`），另有 149 题没有任何 KP 候选——这两类题在「按节派题」的 MVP 主线里无处安放，界面必须写三处特判（UX 评审第 5 条已给出同样的结论）。等 P3 改 `knowledge_points/801.json` 形状时，KP uid 稳定（`K801-12.1-01` 由 framework_gen 生成），但节的归属仍只挂在 `topics` 这个 legacy 字段上，届时要么把 `topics` 提升为 required，要么给题目补 `section_ref`——两条路都要动 1128 题与 7 屏里的 3 屏。

## 4. 对 §14 六条自审结论逐条表态

| # | 自审结论 | 表态 | 理由（一句） |
|---|---|---|---|
| 1 | 版本历史写 `content/history/<entity>/<uid>.jsonl`，一行一字段 | **反对** | git 已经逐行提供 diff/blame/revert，history 是第二份真相；而 P1 一轮要改 6768 个字段值，按「一行一字段」追加就是 6768 行噪声，反而毁掉「可评审」这个原始目标。改为每批次一条 migrate 记录 `{ts, script, git_sha, field_set, count}`，字段级历史只在 `edge.review` 与 `question.answer_spec` 两类高价值字段上按需开。 |
| 2 | 掌握度只走 `mastery_view.compute(evidence_rows, mastery_spec)` | **同意（有条件）** | 方向对，但 `mastery_spec` 现在 registry 里根本不存在（G1），且同一格又说是独立 `mastery_spec.json`——必须先定一个来源（建议：registry 里 `mastery_spec` 为源，构建时写进切片 manifest），否则运行层与私层会各算一遍，出现两套掌握度。 |
| 3 | `capabilities` 与字段白名单共源，能力开但字段缺失 → 构建失败 | **反对** | 两者粒度不同（能力 9 项 vs 实体×字段），且「构建失败」会与已声明的空壳冲突：131 节无题、574 点 `title_only`、`kp_tags` 149 题无候选——构建将永久红，等于取消常态构建。改为「能力缺失 → 切片不带该 capability + report 写一行降级理由」，与 `capabilities` 的设计初衷（前端按能力降级）一致。 |

## 5. 如果只能改一处字段设计

**改 `answer_spec`**：把 `{canonical, equivalent[], tolerance, unit, unordered, answer_type}` 换成 `{answer_status, values:[{raw,kind,role}], order_policy（缺省 any）, tolerance, unit, answer_type, how}`。
理由就一条：判错会写进只追加的 `learner_evidence` 且不可回溯，而 `kp_tags` 这类标签错了可以重算——错误成本不对称，先修不可逆的那个。
